## Problem Statement

A plant's energy meters form a tree: one main meter, department meters under it, line meters
under those, machine meters at the bottom. Every kWh that a machine meter records is also
recorded by its line, its department and the main meter. A query that sums a main meter
together with its child meters counts the same kWh twice. The query runs without error and
returns a plausible number.

A model that writes SQL directly can produce that query. This project shows the alternative:
the model fills a structured request, and deterministic code that knows which hierarchy levels
may be summed compiles the request to SQL. A benchmark measures both ways on the same questions.

The reader is a hiring manager for Forward Deployed Engineer roles at an AI software company.
They give the repository two minutes. The project must look like a finished customer deliverable.

## What Makes This Cool

The public comparison found for this design is a dbt Labs post on semantic layer versus
text-to-SQL (https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026, published
2026-04-07, read on 2026-11-11). The post does not discuss double counting; its failure
examples are incorrect joins and bad aggregations across tables.
This failure is different. It happens inside one table and no
join is wrong. Table definitions cannot state the rule "these levels may not be summed
together"; the benchmark measures whether stating it in prose is enough. The repository shows one wrong number, the SQL
that produced it, and the short declaration under which a request that adds a meter to its
own ancestor does not compile.

## Premises

Agreed by the owner on 2026-11-11.

1. **The reader sees only the top of the README.** That is where one results table and one
   double-counting example go: question, wrong SQL, wrong number, right number. Everything else
   is evidence behind a link.
2. **The baseline is strong.** The text-to-SQL arm gets the same model and a documented schema
   that states every aggregation rule the semantic layer encodes. The dbt Labs post cited
   above reports that adding three denormalised models to the schema moved text-to-SQL from
   64.5% to 90.0% with Claude Sonnet 4.6 (84.1% with GPT-5.3 Codex), on 11 questions run 20
   times each. That is a better-prepared schema, not documented aggregation rules, so it
   supports "preparation helps text-to-SQL" and nothing more specific. A weak baseline
   would make the result worthless to an informed reader.
3. **The question set is honest.** Three groups: hierarchy questions where double counting is
   expected, control questions where text-to-SQL should do well, and out-of-scope questions
   that the semantic layer cannot express and therefore refuses. Refusals get their own column.
   Added on 2026-11-11 with the owner's agreement: a fourth small group of unanswerable
   questions, where refusing is correct.
4. **The public demo spends nothing.** The hosted page replays saved answers and holds no
   API key. Free-text questions run only from a local clone, with the reader's own key
   (owner's decision, 2026-11-11). The 20 EUR budget is for the benchmark only.
5. **Version 2 is data only.** The solar meter, the battery and the production orders table
   exist in the database. Version 1 uses production orders for one metric, energy per unit.
   No scheduling code is written.

## Approaches Considered

### Approach A: own semantic layer, two benchmark arms (chosen)

One file declares metrics, how each aggregates and which hierarchy levels may be summed. A
small deterministic compiler turns a structured request into SQL. The agent, the MCP server
and the benchmark all call the same function. Benchmark arms: text-to-SQL with documented
schema, and the semantic layer.

### Approach B: existing open-source semantic layer engine

Rejected as a judgment about readability and dependency size: the reader should be able to
read the rule and the compiler in this repository, without learning an engine. Whether an
existing engine expresses "do not sum a meter with its ancestor" natively has not been
checked. The stack research records what it finds in the "semantic layer" row of
`docs/stack.md` as the alternative rejected; the choice of Approach A stands.

### Approach C: Approach A with a third arm (text-to-SQL on the undocumented schema)

Rejected for this version. It answers "how much is documentation worth" with a number, but
costs about 50% more paid calls and widens the table at the top of the README.

## Recommended Approach

Approach A.

### Data (generated, deterministic from a seed)

- `meter`: id, name, level (`site`, `department`, `line`, `machine`), parent id, kind
  (`consumption`, `generation`, `storage`).
- `reading`: meter id, timestamp, kWh, one row per meter per 15 minutes. The timestamp is
  the start of the interval, stored in UTC. Days, months and tariff bands use the plant's
  local time (Europe/Rome), so the two clock-change days have 92 and 100 intervals.
- The generator also writes, on every reading, the local start time with its UTC offset, the
  start of its hour, day and month in the same canonical form, the local date and the tariff
  band. Both arms can group by a ready column; neither has to build a timestamp string. Queries group by these columns, so no SQL in this project
  needs time-zone functions and the design does not depend on the database engine having them.
- `tariff`: price per kWh for three bands, defined by local hour and day of the week
  (Monday to Friday, Saturday, Sunday). Public holidays are ignored. Prices are fixed for
  the whole dataset.
- `production_order`: line, product, start, end, units produced. Start and end are UTC
  and fall on 15-minute boundaries. The generator never
  overlaps two orders on one line, and an offline test asserts it, so spreading units over
  time cannot multiply rows.
- **Consumption tree.** The main meter is the plant's total load. Every consumption meter
  except the main meter has a consumption parent. Each parent reads between 3% and 8% more
  than the sum of its children (unmetered load and losses); the generator draws the margin
  per parent inside that range, and it holds in every 15-minute interval. So a node's total is that node's own meter, never a sum of a
  lower level. Summing the machines to get the site total is a second wrong answer: it
  undercounts.
- **Solar and battery.** One `generation` meter and one `storage` meter. They have no parent
  and no level, and are not part of the consumption tree, so the margin rule above is
  unaffected. The default node of a request is the main consumption meter. Solar kWh
  is zero or positive. Battery kWh is signed: positive when discharging, negative when
  charging.
- **What version 1 does with them.** The four metrics below read `consumption` meters only.
  `cost_eur` prices the plant's load at the tariff and ignores solar and battery. Questions
  about solar, battery or orders alone can be answered from the database but not through the
  semantic layer; they belong to the out-of-scope benchmark group (Open Question 7).
- **Realistic load.** Machines draw a standby load when idle and a working load while an
  order runs on their line, so consumption follows shifts, weekends, two plant closures and
  production. Solar follows daylight and season; the battery charges at midday and
  discharges in the evening. A flat or random profile would make trends, peaks and energy
  per unit meaningless to a reader who knows plants.
- **Reference date.** The dataset ends on a fixed date written in the database. The demo
  gives that date to the model as "today". Benchmark questions use absolute dates only.

### Semantic layer (one file)

Four metrics, each with its aggregation rule:

| Metric | Over time | Across meters |
|---|---|---|
| `consumption_kwh` | sum | sum over the request's meters |
| `peak_kw` | max over timestamps | per timestamp, sum the interval kWh of the request's meters and multiply by 4; then take the max (coincident peak, average kW over a 15-minute interval) |
| `cost_eur` | sum of kWh times the tariff price of the interval | same as consumption |
| `energy_per_unit` | total kWh divided by total units, never an average of ratios | one line at a time |

`energy_per_unit` details: the kWh is the line's own meter. Units of an order are spread
evenly over the order's duration, so a period or grain boundary takes its share. The metric
accepts a single line, or the site or a department broken down by line; any other scope fails
at compile time. If units in a cell are zero, the value is null.

Hierarchy rules, which apply to all four metrics:

- A request names a node (default: the site) and an optional breakdown level.
- With no breakdown, the result is the node's own meter. The compiler never sums a lower
  level to produce a node's total.
- With a breakdown, the result has one row per descendant at that level. Rows are not added
  together. The breakdown level must be strictly below the node's own level; anything else
  fails at compile time with a message.
- A request may instead name an explicit list of meters to add up (for example two lines).
  If one meter in the list is an ancestor of another, or the same meter appears twice,
  compilation fails with a message that names the meters. No SQL is produced.
- A request whose node or list names the `generation` or `storage` meter fails at compile
  time with a message saying the metric covers consumption meters only. The compiler never
  filters such a meter out silently.

What this guarantees and what it does not: no request can count the same kWh twice. An
explicit list of all machines is still a valid request and still undercounts the site; that
is a wrong choice by the model, and both arms are scored against it.

### Structured request and compiler

- One request type: metric, scope (node with optional breakdown level, or a list of meters),
  period, time grain, and an optional split by tariff band (consumption and cost only).
  Grains are a closed set: `15min`, `hour`, `day`, `month`, and `total` for one value over
  the whole period (the default). A period is half-open, start included and end excluded,
  in plant local dates.
  There are no other dimensions or filters in this version; a question that needs one is
  out of scope.
- Metric names, levels and grains are closed sets taken from the semantic layer file. Meter ids must exist in the `meter` table. Anything else is rejected
  before any SQL is built. Values are passed as bound parameters. Offline tests send a
  hostile request, a list with a repeated meter, a request naming a non-consumption meter,
  and a breakdown level not below its node, and expect a rejection each time.
- Result columns have one canonical form. Key columns: `meter_id` (the meter's id, never its
  name), `bucket_start` (the start of the time bucket at the requested grain, in the plant's
  local time, ISO 8601 with the UTC offset, for example `2026-10-25T02:00:00+01:00`),
  `tariff_band`. The value column is named `value`. Which keys appear is fixed by the
  request: `meter_id` only with a breakdown (a summed list has none), `bucket_start` for
  every grain except `total`, `tariff_band` only with the split. An offline test compiles an
  hourly request over the autumn clock-change day and expects 25 distinct buckets.
- `compile(request)` is a pure function that returns SQL and bound parameters. It is the only
  code in the repository that produces SQL for the agent, the MCP server and the demo.
- `query(request)` is the one entry point every caller uses: the agent tool, the MCP tool,
  the demo and the benchmark. It validates, compiles, executes and returns the rows together
  with the SQL. It alone owns the read-only connection, the 5,000-row limit and the
  10-second limit; beyond either limit the caller gets an error that says so.
- A period that falls partly or wholly outside the dataset is a compile error that states
  the dataset's first and last date. It never returns an empty result silently.
- The metric catalogue shown to the model and the tool's input schema are generated from the
  semantic layer file, never written by hand. `docs/schema.md` is prose and is written by
  hand; every rule in the layer has an id, and an offline test fails if an id is missing
  from `docs/schema.md`.

### Code layout

One Python package with six modules: data generator; semantic layer and compiler (with
`query`); agent; MCP server; benchmark (harness and scorer); demo server. One frontend
folder with the single page. Tests mirror the modules.

### Agent

The model receives the metric catalogue and the meter tree. It has two tools: `query_metric`,
which accepts the structured request, and `refuse`, which takes a reason. It never sees a SQL
interface. A compile error is returned to the model as the tool result.

### MCP server

Three tools: list metrics, list meters, query a metric. The third takes the same structured
request and calls the same function. The server runs locally from a clone; it is not hosted.

### Benchmark

**Questions.** About 45 in a committed file, in five groups: hierarchy, control (plain
single-meter sums), metric definition (energy per unit, clock-change day, period
boundaries: hard for reasons other than hierarchy, reported separately so they do not blur
the comparison), out-of-scope and unanswerable. The first three have an answer in the database; out-of-scope
means "answerable from the database, not expressible in the semantic layer". Some hierarchy
questions carry the trap in their wording (for example a department together with one of
its own lines), each with a defined correct answer, so the compile-time check is exercised
by the benchmark and not only by unit tests. Unanswerable
questions (about 4, reported as counts, not percentages) ask for something the data does not contain, such as a department that
does not exist or a date after the dataset ends; the correct outcome is a refusal. Every
question uses absolute dates and declares its output shape: the key columns and one numeric
value column. `/eval-plan` fixes the final count per group.

**How the questions read.** Each question is written in the words a person at the plant
would type: meter names as people say them, mixed registers, no shared template. The answer
format is a fixed sentence appended after the question, identical for both arms, so the
user's words never carry it. The questions are written to resemble real ones and are not
logs of real users; the dataset card says so.

**Where the questions come from.** The question types are the ones an energy management
system is asked every day. A first list is drafted from public practice (energy performance
indicators as in ISO 50001 and ISO 50006), then corrected by the owner from memory. No
production system is opened to write them. Each question records its source (`public
standard`, `author, from practice` or `error class Pn`, from a list of generic error classes
prepared in a separate session and reviewed by the owner), its group and the mistake it tests. Questions dropped
during review stay in the file under `rejected`, each with its reason.

**Ground truth, computed twice.** Each answerable question has a hand-written reference
query, and a second computation of the same answer in plain Python over the raw readings,
written without reading the query. An offline test fails if the two disagree beyond the
scoring tolerance. Neither benchmark arm produces either one. Both are written from the same
specification, so this catches slips, not a shared misreading of a rule. Two further checks
cover that: totals the generator knows by construction are asserted directly, and the owner
checks a sample of answers by hand. `docs/golden.md` says exactly this and does not call the
answers independently verified.

**Owner review.** A committed review log records, with its real date, which questions the
owner read, which he changed and which he rejected.

**Dataset card.** `docs/golden.md`, one page: how the set was built, what was verified and
how, what was not, and its limits (one synthetic plant, one model, one run date).

**One command.** A single command rebuilds the database from the seed and re-verifies every
reference answer both ways, offline and without an API key.

**Arms.** Same model, same settings, same loop:

| | Semantic layer arm | Text-to-SQL arm |
|---|---|---|
| Context | metric catalogue, meter tree | `docs/schema.md`, meter tree |
| Execution tool | `query_metric` | `run_sql` (read-only, same 5,000-row and 10-second limits) |
| Refusal tool | `refuse` | `refuse` |
| Errors | returned to the model | returned to the model |
| Tool calls per question | at most 4 | at most 4 |
| Told in the instructions | 4 calls in total; the last successful execution call is the answer | the same |
| Prompt caching | on, one breakpoint at the end of the fixed part (tools, instructions, catalogue, meter tree) | on, same placement (tools, instructions, `docs/schema.md`, meter tree) |

Prompt caching is on in both arms and in the demo. The question is the only part of the
prompt that changes, and it comes after the breakpoint. The results file records, per run,
uncached input tokens, tokens written to cache, tokens read from cache and output tokens, and
cost is computed from all four. A fixed part below the model's minimum
cacheable length is not cached and gives no error, and the semantic layer arm's fixed part
is small, so the harness records cache reads per arm as a fact and reports them. It fails
the run only if neither arm ever reads from cache. Prompts are never padded to reach the
minimum.

`run_sql` executes SQL written by a model on the machine that runs the benchmark. A
read-only database is not enough: some engines still let a query read or write other files.
The database instance behind `run_sql` has file and network access switched off, and offline
tests check that a query trying to read a local file, write a file or attach another database
fails, and that the already-open database stays readable. In DuckDB these settings apply to
the whole instance and cannot be undone until it closes, so the benchmark opens the file
read-only in its own process, after the generator has closed it. The engine's documentation
says these settings are not a substitute for a sandbox: this protects a local benchmark run
and nothing in this repository calls `run_sql` sandboxed.

`docs/schema.md` is a committed, reviewed file. It states in prose every rule the semantic
layer encodes: parent meters include their children; a node's total is its own meter and not
a sum of lower levels; peak is coincident and is interval kWh times 4; cost uses the tariff
of each interval; energy per unit is a ratio of totals with orders spread over their
duration, and is null when no units were produced; the four metrics read consumption meters
only; timestamps are UTC interval starts; days, months and tariff bands use the local-time
columns, including on the two clock-change days; a period includes its start and excludes
its end. The output shape is written inside the question text, and both arms receive the same
question text byte for byte. The
token cap per question is set in `/eval-plan`.

**What is scored.** The rows returned by the last successful execution-tool call of the run,
or the `refuse` call if that is how the run ended. The model's prose is never read. The
compiler emits the canonical column names and forms defined above; the reference queries use
them; both arms see the same names and forms in the question text. The scorer maps
columns by name: a result must contain the key columns the question declares and `value`;
extra columns are ignored; a missing one makes the run "other wrong". It then matches rows by
the values of the key columns, comparing `bucket_start` as a parsed instant and not as a
string; the value column is compared
numerically with a relative tolerance of 0.1% (an absolute tolerance of 0.001 when the
reference is zero), and a null matches only a null; row order is ignored unless the question asks
for an order.

**Outcomes.** Every run ends in exactly one:

| Outcome | Meaning | Counts as correct |
|---|---|---|
| correct | rows match the reference | yes |
| known wrong value | rows match a wrong value listed for the question | no |
| other wrong | rows match neither | no |
| refusal | the run ended with `refuse` | only in the unanswerable group |
| no answer | no successful execution and no refusal within 4 tool calls, or the reply was cut off at the output limit | no |

In the hierarchy, control and out-of-scope groups a refusal is never correct: the person
asking got no answer. In the unanswerable group a refusal is the only correct outcome, and
any returned rows count as "other wrong". Accuracy for an arm and group is
correct runs divided by all runs in that group.

The report also counts runs where an earlier call returned the correct rows and the last
call did not, per arm, because the last-call rule can penalise a model that checks its work.

**Known wrong values.** The listed wrong answers are examples, not a complete list, so the
count of double-counting runs is a lower bound and the README says so. Each hierarchy
question lists the wrong answers a mistaken aggregation would give. Each is a complete row set, compared with the same rules as the
reference, and has a category: `double_count` (a meter added to its
ancestor), `children_sum` (a lower level summed in place of the node's meter),
`separate_peaks` (individual peaks added where the coincident peak was asked) or
`extra_rows` (a breakdown that also contains a row from another level). A result with rows
the reference does not have, or without rows it has, is never correct. The report
counts the two categories separately. An offline test asserts that every listed wrong value
differs from the reference by more than the 0.1% tolerance; the 3% to 8% margin is what
makes that hold.

**Repeats.** Each question runs several times per arm. `/eval-plan` fixes the count and the
minimum count below which no comparison is claimed. Runs are ordered by repeat: repeat 1 of
every question in both arms, then repeat 2, and so on. Before each repeat the harness checks
that it fits in the remaining budget; if not, it stops there. Both arms and all groups
therefore always have the same number of runs, and accuracy is computed over completed
repeats. If fewer repeats than the minimum completed, the README block shows the counts and
says the run is below the minimum, with no comparison claim. The results file also records,
per question, how many runs were correct.

**Budget accounting.** The 20 EUR includes the priced pilot that `/eval-plan` runs. Provider
prices in another currency are converted at one fixed rate, set in `/eval-plan` and recorded
in the results file.

**Harness failures are not model failures.** An API error after retries, a rate limit, a
timeout or a harness bug is not an outcome. That attempt goes to a separate errors file with
its cause and is run again; it never enters the accuracy denominator. Retries use backoff
with jitter and are counted per run. Each run has a wall-clock limit.

**Provider refusals.** The API can decline a request on its own (stop reason `refusal`).
That is different from the model calling the `refuse` tool. It is recorded as "no answer"
with its cause. Automatic fallback to another model is off in the benchmark, because a run
answered by a different model measures nothing; it may be on in the demo.

**Settings.** Both arms set the same effort level explicitly. Current models do not accept
sampling parameters, so run-to-run variation is expected and is the reason for repeats. The
harness reads the model name from every response and fails the attempt if it is not the model
requested.

**Scorer self-test (offline).** Before any paid run: the reference rows scored against
themselves must come out 100% correct; an empty result and a constant answer must come out
0%; each known wrong answer must be classified in its category.

**Transcripts.** Every run saves all messages, tool calls, tool results and the scorer's
inputs and outputs, so any score can be traced without running again. The example at the top
of the README links to one of these.

**Uncertainty.** The two arms answer the same questions, so the comparison is paired. The
report gives the difference between arms with a 95% interval, per group. With about 12
questions in a group and 3 repeats the interval is roughly plus or minus 17 points, so
`/eval-plan` must set the number of questions and repeats from the smallest difference worth
reporting, and the README states the interval next to every accuracy figure.

**Versions.** The results file records the dataset seed, a hash of the questions file, of
the scorer and of both prompts, and the dependency lock file is committed. Results produced
with different versions are not compared.

**Report.** Per arm and per group: accuracy, refusals, known wrong values by category,
no-answer runs, cost. Results are written to a committed file.

**README numbers.** The results table and the example are generated from the results file
into a marked block of the README. An offline test regenerates that block and fails if it
differs. Numbers outside the block are not results and are not checked.

**The headline number.** The first figure in the block is, per arm, how many runs delivered
a wrong value without any warning (known wrong value plus other wrong), out of the runs
scored. Next to it: accuracy per group and cost per correct answer. A single overall
accuracy is not shown, because out-of-scope refusals cap the semantic arm below 100% by
design and one percentage would hide that.

**The example at the top of the README.** It is taken from a recorded benchmark run and
links to that run in the results file. If no run produced a `double_count`, the block states
that finding instead, and reports what remains: refusals, cost, and that one arm cannot
build the double-counting query while the other did not build it this time. A hand-written
illustration may appear lower in the README, labelled as an illustration.

The result is published whatever it shows.

### Demo (one page)

Wireframe: `agentic-ems-demo-sketch.png`, next to this document (numbers in the sketch are
illustrative).

- Question input with four sample questions. Streamed answer, a chart under it, and the
  structured request beside it.
- The text-to-SQL arm exists only in the benchmark. The demo never executes SQL written by
  a model.
- Sample questions are saved answers: the text, the structured request and the result rows.
  They are replayed as a stream and cost nothing. An offline test fails if a saved request
  no longer compiles to the saved rows.
- The hosted demo is a static page: it replays the saved answers from files and says so in
  one line, with the command to run free-text questions from a clone. It has no server, no
  API key, no database and nothing to rate-limit.
- Free-text questions run from a local clone: the demo server listens on localhost only and
  reads the reader's own API key from the environment. Each request is bounded: maximum
  question length, maximum output tokens, at most 4 tool calls.
- Chart: a line for a time series, bars for a breakdown, no chart for a single value, a
  refusal or an error.
- Every number shown as the answer is rendered by code from the result rows. The model's
  text is commentary under it, so a figure misquoted by the model cannot be the headline.
- States: streaming, out of scope, no API key (local only: one line saying which variable
  to set), error (one line, no stack trace). Sample questions work in every state.

### Not in this version

Redis: saved answers are files and nothing else needs a store. A hosted free-text demo:
it would add a server holding a key, a per-visitor rate limit and a spend cap for a reader
who clicks a sample. Ranking ("top five machines"): common in practice, but it adds a
concept to the compiler; it stays an out-of-scope benchmark question (owner's decisions,
2026-11-11). Ragas or any LLM-judged evaluation: there is no
retrieval here, and scoring is an exact comparison with a reference (owner's decision,
2026-11-11).

Production scheduling, weather forecast, solver. Authentication. More than one plant. More
than one database engine. Theming. Any text-to-SQL in the demo. Semantic-layer metrics
for solar, battery or orders alone.
